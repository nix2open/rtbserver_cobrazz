# Оптимальная ставка OpenRTB — инструкция для агента

**Дата:** 2026-11-27, дополнение в тот же день: `win_price` и процент по source  
**Стек:** FE `OpenRtbBidRequestState` → async-лог → ClickHouse `click00` → UI на `adbe05`  
**Трафик:** только OpenRTB (`/openrtb`). Google, Yandex, Adfox, DAO, AdJson не трогать.  
**Релиз FE:** только по `docs/RTB_RELEASE.md`. Canary: `adfe103`. Рестарт только `tr*-FCGIRtbServer`.

Эта инструкция фиксирует решение. Не выбирать архитектуру заново и не ставить отдельный синхронный post-bid сервис.

---

## 1. Что это

Сервис считает рекомендуемую ставку для уже выбранного креатива и, в зависимости от режима, подменяет `seatbid.bid.price` в OpenRTB-ответе.

| Режим | Поведение |
|---|---|
| `off` | Ставку не трогать. Модель не вызывать. |
| `shadow` | Посчитать и записать в лог. В ответ уходит исходная ставка. |
| `margin` | Если расчёт **ниже** исходной ставки — подменить. Если расчёт **выше или равен** — отправить как есть. |
| `optimal` | Подменить и вниз, и вверх, в пределах потолка из §5. |

`margin` — сохранение маржи. `optimal` — оптимальная закупка. Оба режима включаются только после `shadow`.

Экономия возникает на first-price: биржа списывает нашу ставку. На second-price занижение ставки денег не сохраняет, только проигрывает аукцион. OpenRTB по умолчанию `at=2` (second-price). Поле `at` сейчас в `RequestInfo` не сохраняется.

## 2. Решение по мощности и месту

**На текущих машинах сервис строится.** Отдельный кластер и GPU не нужны.

Почему хватает CPU на FE:

- Считать надо только когда креатив уже выбран, а не на всём ingress. Снимок 2026-11-24: ~5.5–6k OpenRTB RPS на хост, ~115k RPS на ферму, bid response ~0.055%, timeout ~93%. Это снимок, не контракт: фаза 0 обязана перемерить именно число OpenRTB-бидов.
- Показы за 2026-11-26 (`default.RImpression_recent`): **10 040 321**. Даже при win rate 10% это порядка 1k бидов/с на ферму, десятки на один FE. Дерево (XGBoost/CatBoost) на таком объёме — доли миллисекунды. XGBoost в `CampaignManager` уже считается на более тяжёлом пути.
- Обучение офлайн, на `click00` или `dev02`. Хосты `nvidia00`/`nvidia01` с ноутбука не открываются и для v1 не нужны.

**Куда ставить: расчёт на каждом FE, настройки в одном месте.** Не один post-bid прокси на все ответы.

| | На каждом FE | Один синхронный post-bid |
|---|---|---|
| Где цена | Уже есть: `OpenRtbBidRequestState.cpp`, `add_number(PRICE)` после `limit_max_cpm_` | Пришлось бы заново парсить JSON, который FE только что собрал |
| Задержка | Вызов функции на редком биде | Лишний сетевой хоп при и так ~93% timeout |
| Отказ | Ошибка модели → исходная ставка | Падение ящика на денежном пути |
| Объём | Десятки бидов/с на хост | Отдельный сервис нечем загрузить |

Один «контрол» — это файл настроек и файл модели, одни на все FE. Не процесс, через который проходят bid response.

Путь Yandex в том же файле (`Response::Yandex::PRICE`) не менять.

## 3. Что уже известно и чего не хватает

Замер `click00`, `RImpression_recent`, `event_date = yesterday()` на 2026-11-26:

| Факт | Значение |
|---|---|
| Показы | 10 040 321 |
| `win_price == bid_price` точно | 9 889 375 (**98.5%**) |
| `win_price` ниже ставки больше чем на 2% | 22 318 |
| `win_price` выше ставки | 0 |
| `colo_id` / publishers / tags | 1 / 23 / 168 |

**Что такое `win_price`.** Это цена, которую подставила биржа, обрезанная сверху нашей ставкой. Не копия, записанная в момент бида.

Проверено на `adfe103` 2026-11-27, снято с провода:

| Что увидели | Пример |
|---|---|
| В исходящем OpenRTB-ответе в notice/pixel | буквальный `p=${AUCTION_PRICE}`, не число ставки. Источники в том же ответе: `src=adr`, `src=slt`, `src=silvermob`. URL: `https://ad.new-programmatic.com/track.png?...&p=${AUCTION_PRICE}&t=n` и `http://ad.new-programmatic.com/inst?...&p=${AUCTION_PRICE}` |
| Во входящем notice несколько секунд спустя | биржа подставила число: `&p=29.426524` (`src=adr`, vast), также `&p=50` и `&p=40` |

Дальше по коду, без развилки:

1. `ImprTrackFrontend`: параметр `p` разбирает `OpenPriceProcessor` с делителем **1000**. `p=29.426524` → `pub_imp_revenue = 0.029426524`, тип absolute, запрос помечается OpenRTB. Нечисло (`${AUCTION_PRICE}` без подстановки) в revenue не пишется.
2. `RequestInfoContainer::eval_revenues_on_impression_fin`: в доход паблишера берётся `min(доход_из_ставки, цена_из_p)`.
3. `ResearchImpressionLogger`: `win_price = этот_доход * 1000 / currency_rate`. При курсе 1 и нулевом coef `win_price` равен меньшему из ставки и `p`.

Отсюда 98.5% точных совпадений и ноль строк, где `win_price` выше ставки: на first-price биржа присылает `p` равный нашей ставке, а если пришлёт больше — `min` всё равно оставит ставку. Занижение `seatbid.bid.price` меняет и то, что вернётся в `p`, и `win_price`. Цифру «сохранили» считать по `win_price` побед можно.

`source_id` в запросе — query-параметр `src` (`/openrtb?src=adr&aid=...`). В `RImpression` его нет, в новый лог его писать обязательно.

Данных для модели сейчас нет:

- Таблицы бидов (`RBid`) в ClickHouse нет. Проигрыши не видны, есть только победы.
- В `RImpression` нет `source_id`. `colo_id` один на все строки, это не источник.
- `BidRequest.at` на FE не разбирается.

Источник в коде — `request_info.source_id` (то же значение уходит в метрики как ssp). UI режет статистику по нему.

## 4. Поведение на бид-пути

Точка изменения: только OpenRTB-ветка, сразу после расчёта `openrtb_price` и до `bid_object.add_number(PRICE)`.

`original` — ставка, которую FE отправил бы сегодня (уже после `limit_max_cpm_`), в тех же единицах, что `seatbid.bid.price` (CPM, `sum_pub_ecpm / 100`). Модель говорит в этих единицах, не во внутренних 0.01 CPM.

Порядок:

1. Есть файл-выключатель `bid_price.disable` → `off`.
2. Взять режим и процент: блок `sources[source_id]`, если он есть, иначе `default_mode` и `default_percent`. Режим `off` или процент 0 — исходная ставка, строку лога не писать.
3. Бакет. `hash(request_id) % 100 >= percent` → исходная ставка, модель не вызывать, `reason=holdout`. Хеш стабильный и одинаковый на всех FE. Не `rand` и не адрес хоста: один и тот же запрос всегда в одной группе. Процент источника не умножается на общий процент, а заменяет его.
4. `deal_id` не пустой → не менять, причина `deal`.
5. `at != 1` или `at` неизвестен → не менять, причина `not_first_price`. Не угадывать first-price.
6. Валюта пола и валюта ставки различаются → не менять, причина `currency`.
7. Модель не загружена или расчёт дольше **0.5 мс** / кинул исключение → исходная ставка, причина `no_model` или `inference_error`.
8. Иначе кандидат по режиму:
   - `shadow`: в JSON пишется `original`, в лог — оба числа.
   - `margin`: `price = min(original, model)`. Если `model >= original` — причина `kept`.
   - `optimal`: `price = model`, затем снова прогнать через `limit_max_cpm_` и потолок `original * (1 + max_uplift)`.
9. `price < bidfloor` → поднять до `bidfloor`, если `bidfloor <= original`. Иначе отправить `original`, причина `below_floor`. Ниже пола не отправлять.
10. `price <= 0` → `original`, причина `bad_price`.

Меняется только число `price` в bid object. `adm`, `nurl`, `burl` и цена рекламодателя не переписываются: клиринг подставляет биржа (`${AUCTION_PRICE}` / `{winning_price}`).

Любая ошибка — исходная ставка. Сервис не имеет права превратить бид в nobid и не имеет права задержать ответ дольше бюджета 0.5 мс.

## 5. Настройки (один контрол на все FE)

Три файла, одинаковые на каждом FE. Образец — `inventory_sample`: FE перечитывает их сам, рестарт для смены режима не нужен.

| Файл | Смысл |
|---|---|
| `/opt/foros/server/var/run/bid_price.disable` | Есть файл → глобальный `off` |
| `/opt/foros/server/etc/bid_price.json` | Режимы и потолки |
| `/opt/foros/server/etc/bid_price_model.bin` | Модель. Нет файла → расчёт пропускается, ставка исходная |

`bid_price.json`:

```json
{
  "default_mode": "off",
  "default_percent": 0,
  "max_uplift": 0.15,
  "max_shade": 0.30,
  "sources": {
    "adr": { "mode": "margin", "percent": 10 },
    "slt": { "mode": "shadow", "percent": 100 }
  }
}
```

`source_id` — значение `src` из `/openrtb?src=...`.

- `default_mode` и `default_percent` действуют на источники без своего блока. Так включается доля всего трафика, без перечисления source.
- Блок в `sources` заменяет оба поля для этого source. Проценты не перемножаются: у `adr` в примере 10%, даже если `default_percent` другой.
- `percent` — целое 0…100. Нет поля `percent` у source → берётся `default_percent`, не 100. Чтобы забрать весь source, писать `100`.
- Число вне 0…100, не число, неизвестный режим → для этой записи режим `off` и процент 0. Файл целиком при этом не отвергать: остальные source продолжают работать.
- `default_mode` остаётся `off`, пока фаза 4 не пройдена хотя бы на одном source. Общим процентом ферму не включать.
- `max_shade`: в `margin` модель не опускает ставку сильнее, чем на эту долю от `original` (0.30 = не ниже 70% исходной).
- `max_uplift`: в `optimal` потолок над `original`. В `margin` не используется.

Пример выше: 10% бидов `adr` в `margin`, все биды `slt` в `shadow`, остальные source выключены. Срез «часть трафика одного source» и срез «весь указанный source» задаются одним файлом.

Менять JSON на одном FE (canary), потом копировать на остальные. Поднять процент source с 10 до 100 — правка этого файла, без релиза.

Модель кладётся рядом с бинарём тем же релизом, что и код загрузки. Смена файла модели без смены режима допустима: FE подхватывает новый файл, при ошибке чтения остаётся предыдущая модель или `off` для расчёта.

## 6. Модель v1

Одна модель: градиентный бустинг, который уже есть в репозитории (CatBoost в тренерах или XGBoost, как `CTR::XGBoostPredictorPool`). Нейросеть на бид-пути не ставить.

Признаки, все известны в момент ответа: `source_id`, `tag_id`, размер, формат (banner/video/native), страна, тип устройства, `bidfloor`, `original`, `predicted_ctr`, `at`.

Метка: `won`. Единица, если `request_id` бида нашёлся в показах, иначе ноль. Лог бидов пишется на каждый OpenRTB-бид (или на детерминированный семпл, см. фазу 1). Без проигрышей модель не учить.

Формула ставки: перебрать несколько коэффициентов от `1 - max_shade` до `1 + max_uplift` шагом 0.05, для каждого оценить `P(win | price)`. Взять цену с максимальным `P(win) * (original - price)` при ограничении: в `margin` коэффициент ≤ 1. `original` здесь — ценность, которую кампания уже согласилась заплатить.

Пока лога бидов меньше 7 дней — модели в бою нет, режимы `margin` и `optimal` запрещены. `shadow` пишет признаки и `original`, кандидат пустой.

## 7. Лог и витрина

Отдельный async-лог, не в горячем ответе и не внутрь `RImpression`. Сброс пачкой, как InventorySample. Падение записи лога не влияет на ставку.

Поля строки: `event_time`, `request_id`, `source_id`, `tag_id`, `size`, `format`, `country`, `device_type`, `at`, `bidfloor`, `original_price`, `model_price`, `sent_price`, `mode`, `percent`, `bucket`, `reason`, `won` (заполняет джойн, не FE).

`bucket`: `treated` или `holdout`. `percent` — процент, который действовал на этот source в момент бида.

`reason`: `off`, `holdout`, `shadow`, `kept`, `shaded`, `raised`, `deal`, `not_first_price`, `currency`, `below_floor`, `bad_price`, `no_model`, `inference_error`.

Куда: SyncLogs → `click00.default.bid_price_events`, TTL **15 дней**.

Джойн победы: `won = 1`, если `request_id` есть в `RImpression_recent` за тот же день ± соседний. Джойн офлайн, раз в час, не на FE.

Писать строки только по source, у которых режим не `off` и процент > 0. И treated, и holdout: иначе не с чем сравнить win rate.

Объём. Если OpenRTB-бидов такого source на хост **≤ 500/с** — писать 100% его treated и holdout. Если больше — писать детерминированный 10% отдельным хешем (`hash(request_id + ":log")`), плюс счётчики 100%. Хеш лога не совпадает с хешем бакета: иначе 10% оптимизации можно случайно вычеркнуть из лога. Решение бакета применяется ко всем бидам, семплится только запись.

## 8. UI

Минимальная страница на `adbe05`, порт **3091**. Порт **3080** занят инвентарём, его не трогать. Браузер в ClickHouse не ходит: тонкий BFF читает только витрину. Доступ по VPN, без логина, как у инвентаря. Язык русский.

Один экран:

1. Период: сегодня / вчера / 7 дней. По умолчанию вчера.
2. Фильтр источника (`source_id`) и режима.
3. Карточки: бидов treated, бидов holdout, из treated ставка изменена, сумма `(original - sent)` по победам treated где ставку снизили, сумма `(sent - original)` по победам treated где ставку подняли, win rate treated, win rate holdout, число ошибок.
4. Таблица по `source_id`: те же числа, режим, процент. Рядом две колонки win rate: treated и holdout.
5. Таблица ошибок: `reason` и количество. `kept`, `shadow` и `holdout` — не ошибки.
6. Кнопка «Скачать CSV» текущей таблицы.

«Сохранили» = сумма `(original_price - sent_price)` только по строкам `bucket=treated`, `won=1` и `sent < original`. Holdout в сумму не входит. «Потратили сверху» = сумма `(sent - original)` по treated-победам, где ставку подняли.

Пока джойн `won` не готов, карточки экономии показывают «ещё нет сверки с показами», а не ноль.

### Фаза 3. Обучение и shadow-расчёт

Сделать только если фаза 0 подтвердила, что `win_price` — цена клиринга, и в логе ≥ 7 дней, и доля `at=1` у выбранного источника > 0.

Проверка за сутки canary:

- `sent_price = original_price` у 100% строк.
- Доля `inference_error` + `no_model` < 0.1% бидов источника.

Тест: битый файл модели → ставка исходная, процесс FE жив. Юнит режимов из §4 на таблице случаев (ниже / выше / пол / сделка / `at=2` / ошибка модели).

### Фаза 4. Режим `margin` на доле одного источника

Вход: фаза 3 зелёная, источник first-price, в shadow кандидат ниже `original` хотя бы на 5% бидов (иначе экономить нечего).

Сделать:

1. В JSON canary один source, например `adr`: `mode=margin`, `percent=10`. Остальные без блока, `default_mode=off`.
2. Держать сутки. Контроль — holdout этого же source (90%), не другой source.

Проверка, treated против holdout того же source:

- Доля treated ≈ 10% ± 2 п.п.
- Win rate treated не ниже holdout больше чем на **5% относительных**.
- Средний `win_price` побед treated ниже holdout.
- Ошибок `below_floor` / `bad_price` / `inference_error` < 0.1% treated.
- В выборке 100 treated-ответов canary ставка ≥ пола и ≤ исходной. У holdout ставка равна исходной.

Не сошлось: поставить этому source `percent=0` в JSON, не ждать релиза. Разобрать, не катить.

Сошлось: тот же JSON на остальные FE по одному хосту, после каждого — те же пункты за 15 минут. Поднимать процент этого source ступенями 10 → 25 → 50 → 100, на каждой ступени те же пункты за сутки. Другой source включать отдельной записью со своим процентом, не через `default_percent`.

Тест: юнит `margin` — модель выше исходной оставляет исходную; модель ниже пишет min, но не ниже пола и не ниже `original * (1 - max_shade)`.

### Фаза 5. Режим `optimal`

Только на источнике, который прожил в `margin` 7 дней и прошёл проверку фазы 4.

1. Поднять `max_uplift` сначала до **0.05**, не до 0.15.
2. Сутки на canary.

Проверка:

- Доля ставок выше `original` объясняется логом (`reason=raised`), и ни одна не выше `limit_max_cpm_` и `original * (1 + max_uplift)`.
- Win rate не обязан вырасти, но цена победы не выше исходной ценности: средний `sent_price` побед ≤ средний `original` побед этого источника за контрольный день, либо прирост показов покрывает доплату (доплата на победах < прирост числа побед × средний `original`). Если нет — вернуть `margin`.
- Карточка UI «потратили сверху» сходится с суммой по логу ±1%.

Тест: юнит `optimal` — ставка выше потолка обрезается; `limit_max_cpm_` применяется к новой цене, не только к исходной.

## 10. Тесты, которые должны быть до canary

| Случай | Ожидание |
|---|---|
| `off` и файл disable | JSON-цена как раньше, модель не вызывается |
| `shadow` | В логе две цены, в JSON исходная |
| `margin`, модель ниже | В JSON меньшая, не ниже пола и не ниже shade-пола |
| `margin`, модель выше | В JSON исходная, `reason=kept` |
| `optimal`, модель выше | В JSON выше, не выше uplift и не выше max cpm аккаунта |
| `at` пустой или 2 | Цена исходная, `reason=not_first_price` |
| Сделка | Цена исходная, `reason=deal` |
| Модель бросила исключение | Цена исходная, ответ 200 с бидом, не nobid |
| Yandex-ветка того же файла | Цена не изменилась |
| `percent=0` или режим `off` | Цена исходная, модель не вызывается |
| `percent=100` | Бакет treated у всех request_id |
| `percent=10`, 10k разных request_id | Treated 8–12% |
| Тот же request_id дважды | Один и тот же бакет |
| У source свой percent, у остальных default | Считается percent source, default не умножается |
| `margin` и бакет holdout | Цена исходная, `reason=holdout` |

Команда стиля после правок C++: `git diff --check`. Сборка и узкий тест фронта — по правилам репозитория. Если тест не запустился локально, написать почему и прогнать его на `dev02` до canary.

## 11. Не делать

- Синхронный HTTP/gRPC в расчёте ставки.
- Один ящик, через который проходят все bid response.
- Включение `margin` или `optimal` на second-price и на сделках.
- Семпл или запись лога внутри формирования JSON дольше сброса в буфер.
- Правка Google, Yandex, Adfox, DAO, AdJson.
- `yum` на ферму и рестарт `CampaignManager` из-за этой задачи.
- Цифра «сохранили» по всем бидам, а не по treated-победам.
- Случайный бакет (`rand`, время, номер FE). Только стабильный хеш `request_id`.
- Общий `default_percent` на ферму до того, как один source прошёл фазу 4.
- Нейросеть и GPU.
